- 2026-08-30: **Phase 5(同音連打)対応。** 追従器 `follower.py` を見直し、同じ音の連打で数秒遅れる問題を解消した。
  - 原因: (1) 参照オンセットの三角パルスに「楽譜のオンセットが音に無い → 重い」ペナルティを毎フレーム掛けていたため、連打では音符の境目を越えるほうが停滞(無料)より高くつきパスが最初の音符に張り付く。(2) 観測を「予測に最も近い同点列」にしていたため、コストが平坦な区間で観測が予測に引きずられ、列境界の手前で固定点になる(progress にあった「観測ゲインの循環」の正体)。
  - 変更: 観測を同点区間(平坦部)として扱い、予測が区間内なら補正しない・外なら端へ引き寄せる。同じ音が続くブロック(短い無音 ≤ 0.3 拍は橋渡し。スタッカートの連打を含む)では DTW の内部位置を信用せず、テンポと発火カウント(`_snap_to_head`: 発火 1 回 = 予測位置の次の音符の頭。強度 ≥ 0.5、最小間隔 0.5 音価)で進める。発火中に前進ステップで頭の列に入ったときだけ DTW に報酬(`onset_bonus`)。過渡(発火強度に比例)の間は chroma コストを減衰(`transient_damp` 0.5、実演奏で真の経路が過渡ごとに 2〜3 損をして別区間に負けるのを防ぐ)。テンポはイベント(区間下端の上昇・スナップ)の回帰をイベントごとに更新、範囲 0.6〜1.5 倍。休符中は休符の終わりで位置を止め、休符長 + 1 秒まで見失いにしない。遠方ジャンプは「窓が明らかに悪い」か「全体最小が 1 秒以上遠方(平均不足 ≥ 2)」のとき、候補が 1 箇所なら飛び、複数なら再探索(lost)で待つ。再探索の一意判定は 20 フレームの持続を要求。
  - 評価(`tools/eval_follower.py`、変更前 → 後): 合成テンポ変動 全体 中央値 65 → 39 ms・p95 2071 → 527 ms、連打区間(拍 50.5〜63.75)中央値 543 → 22 ms・p95 3199 → 59 ms、弾き直し再アンカー 2.54 → 1.05 s、実演奏 中央値 141 → 125 ms・p95 1437 → 1444 ms。実演奏の残りの大きな誤差はリトルネロ内部の 4 拍反復(拍 9〜12、変更前からある)と連打区間(オフライン整列の正解自体が不確か)。
  - 試して駄目だったこと: 報酬だけ(ペナルティなし)のオンセット項 → 頭が密な区間(B3 の 32 分音符連打など同じ音名)が報酬の磁石になり再探索が壊れる。発火で数えた頭をそのままテンポ回帰に使う → 実演奏の余分な発火で 2 倍のテンポまで暴走する。ジャンプ判定の漏れ積分 → 効果なし。
  - 回帰テスト `tests/test_follower.py`(合成: 連打つきテンポ変動、無音を挟む弾き直し)。
  - ユーザーから「慎重すぎて伴奏してくれない」と指摘 → 実演奏の記録で server の開始条件を再現したところ、一意性 ≥ 0.3 のフレームが 44 % → 26 % に減っていた(過渡の減衰と発火の報酬が「他の場所より良い」証拠を弱める)。一意性の判定用に減衰・報酬なしの累積コスト `Du` を別に持つようにして 36 % に回復。残りの差は曲頭のリトルネロ(設計上一意にならない箇所で、変更前は偶然 2 点の差で通っていた)。この記録では開始イベントは変更前後とも 4〜5 回 / 50 秒で、平滑化や閾値 0.2 でも大差なし。主因は「1 秒間ずっと確実」の条件と楽譜内の反復。追従 ON のまま弾いた記録(`states.jsonl` に追従状態が残る)があれば開始しない理由を正確に再現できる。

- 2026-08-30: ユーザーが追従 ON で 3 本記録(ノクターン 73 s / 218 s、春 254 s)。伴奏が鳴ったのは全体の 15〜20 %。原因を分けると (1) **追従そのものが途中で崩壊**(春 60 s 以降、位置が拍 35〜320 を飛び回る。変更前のコードでも同じ)、(2) 反復の展開されたノクターンでは同一箇所が複数あり一意性が 0 のまま(位置は連続的に進んでいる)。

  - 変更: 取りこぼしのペナルティを毎フレームから「頭の列を通過するときの 1 回きりの遷移コスト」(`onset_miss_cost` 0.5、発火に一致すれば報酬 `onset_bonus` 0.5)に変更。再スタートペナルティ 15 → 30。見失い(lost)に入ったら累積コストを白紙にする(残すと弾き直しの再アンカーが 5 秒かかる)。

  - 残る課題: ノクターンのように反復・類似の多い曲では、オンライン追従は「どのコピーか」を決められない。伴奏の音は同じなので、直前の位置に近いコピーで鳴らしてしまう(継続性を優先)方針を server 側で検討する。追従の評価は `recordings/` の 4 本を `tools/` 化して回帰に使う。

- 2026-08-30: **追従の複数仮説化。** ユーザーの「候補は複数持っているか」に答える形で、`follower.py` の遠方ジャンプ判定(strong / long → 一意なら飛ぶ、曖昧なら lost)を副仮説の並走に置き換えた。毎フレーム、主仮説の窓の最小より `alt_margin`(4)以上良い列のクラスタを副仮説として抽出し、既存の副仮説と位置(3 拍 + テンポ分)で対応づけて `lead`(主仮説より良い状態の累積秒。良くない間は減り、0 で消える)を更新。乗り換えは lead が閾値(現在位置から 8 拍以内なら `alt_switch_near_sec` 1.5、遠ければ `alt_switch_far_sec` 4.0)を超えた副仮説があるときだけで、コストが同点(margin 以内)の候補が複数なら現在位置に近いものを採る。窓が悪いのに副仮説が育っていない間は位置を保持する(確信度が下がるので伴奏側が止まる)。state.follow に `alternates`。

## 注意点

- Python は必ず venv(`core/.venv`)で作業する。
- 楽譜は `scores/<song_id>/`(構成は [../../scores/README.md](../../scores/README.md))。いずれも Violin + Piano の 2 パート、MIDI は format 1・3 トラック(Violin / Piano 右手 / Piano 左手)、480 ppq。
  - `vivaldi_spring_1`: 4/4、♩=70、83 小節、反復なし、弱起 0.5 拍。
  - `chopin_nocturne_op9_2`: 12/8、♩=50、19 小節、反復記号・1/2 番括弧あり。MIDI は展開済み、UI 側は OSMD の展開後時刻で対応。 検証: OSMD の展開後拍は 144.5 拍まで MIDI の発音拍と全点一致(装飾音の細分は除く)。最終小節だけ OSMD 側に 146〜147.5 拍の点が余り、MIDI(146 拍で終了)より 1.5 拍長い。曲末のみの差なので保留。`.mscz` は 20251212 版、`.mxl` / `.mid` は 20250119 版から書き出したものなので、内容がずれていたら書き出し直す。
  - タイスの瞑想曲は `.mscz` がリポジトリに無い(削除済み)。必要なら `scores/massenet_meditation_thais/` に置く。
- 伴奏再生では MIDI の Violin トラックを除外し、Piano の 2 トラックだけを鳴らす。Violin トラックは固定テンポ再生時のカーソル検証に使える。
- この PC には MuseScore 4 の CLI(`MuseScore4.exe`)が既定パスに見つからなかった。書き出しはユーザーが別途行う。
- `package.json`(root)は起動スクリプト用。`version` は 0.1.0。
- Phase 0 の MIDI 音源は Windows 標準の Microsoft GS Wavetable Synth(python-rtmidi 経由)。遅延が大きい(数十 ms 以上)ので、伴奏の同期精度を測る段階(Phase 3〜4)で FluidSynth 等に置き換える。
- WebSocket の配信周期は 30 Hz 指定だが Windows のタイマ粒度で実測 ≈ 21 Hz(47 ms)。UI は requestAnimationFrame で補間なしに描くので、必要なら UI 側で位置を外挿する。
- 再生開始直後に 100〜200 ms 程度の位置オフセットが観測された(クロック自体は正確)。GS 音源への最初のイベント送出が詰まる可能性。Phase 3 で伴奏遅延を測るときに再確認する。
- 弱起の曲は MIDI も MusicXML も拍 0 から始まり整合する。小節番号は MusicXML の `number` 属性(弱起 = 0)を使う。
- Electron のビルド・起動時は環境変数 `ELECTRON_RUN_AS_NODE` を解除する(VS Code のターミナルが `1` を設定し、Electron が素の Node として起動して `app` が undefined になる)。`start.bat` と `npm run dist` 前の手動実行で注意。
- electron-builder は `npmRebuild: false` にする(OSMD が依存する Node ネイティブモジュール `gl` の再ビルドが失敗する。レンダラは Vite でバンドル済みなので不要)。`node_modules` はパッケージに含めない。
- electron-builder の Electron 展開で `win-unpacked.tmp` → `win-unpacked` の rename が EPERM になる環境のため、`electronDist: node_modules/electron/dist` を指定してコピー方式にしている。
- パッケージ版の楽譜は `resources/scores/<song_id>/`(score.mid / score.mxl / song.json のみ同梱)、core は `resources/core/violin_core.exe`。
- 追従器のパラメータは `OnlineFollower.__init__` の既定値(onset_weight 0.5 / onset_miss_cost 0.5 / onset_bonus 0.5 / transient_damp 0.5 / near_eps 0.05 / measurement_gain 0.25 / jump_margin 6 / restart_penalty 30 / snap_min_strength 0.5 / snap_min_interval 0.5)。実演奏の結果はパラメータに敏感(記録が 1 つしかない)なので、変更時は `tools/eval_follower.py` の合成と実演奏の両方を見る。
- オフライン DTW(align.py)の既知の弱点: 同じ音高の長い音の連打(例: 拍 51.5〜53.5 の B5 ×3)では発音時刻が 1〜1.7 秒ずれることがある(chroma が同一でオンセットのピークが弱い)。オンセット特徴の重みは 1.0(`--onset-weight`)。オンライン追従器側は Phase 5 で対応済み。無音判定はノイズ床 +12 dB と chroma ピーク ≥ 0.45 の両方で行う(ノイズだけのフレームは chroma が平坦で、楽譜のどこにでも半端に一致するため)。
- 発音時刻は約 50 ms 遅れて検出される(窓長 4096 = 85 ms の影響)。相対的なタイミング偏差では相殺されるが、絶対時刻が必要な場面では補正する。
- 入力の遅延計測: WASAPI では `inputBufferAdcTime` がコールバック時刻より未来の値を返して信用できないため、PortAudio の `stream.latency`(このデバイスで 22 ms)を引いて AD 時刻の近似としている。
- chroma は ±60 セントのビブラートだと単フレームで隣の半音に主成分が移ることがある(平均では正しい)。DTW に入れる前に時間方向の平滑化か窓長の見直しを検討する。
- 記録の保存先: 開発時はリポジトリの `recordings/`(gitignore 済み)、パッケージ版は `%APPDATA%/violin-accompaniment/recordings/`。
- `start.bat` は ASCII のみで書く(日本語を入れると cmd.exe が UTF-8 を誤解釈して行が壊れる)。メッセージは英語。
- ポート 5173 は他プロジェクトが使っていることがある。`ui/vite.config.ts` は 5173 固定なので、衝突時は `npx vite --port 5199` などで起動する。
- 追従器は最初から自作しない。`matchmaker` の動作確認を Phase 3 の入口にする。
- リプレイ基盤を後回しにしない。Phase 1 の成果物に含める。
- マイク入力で試す場合はヘッドホンを使い、伴奏の回り込みを避ける。
