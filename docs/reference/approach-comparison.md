# 2 案の比較と採用方針

作成日時: 2026-08-30 02:52
更新日時: 2026-08-30 02:52

LLM との検討で得た 2 つのドラフト仕様を比較し、このプロジェクトで採用する方針をまとめる。

- ドラフト A(Claude 案): [draft-spec-claude.md](draft-spec-claude.md)
- ドラフト B(Codex 案): [draft-spec-codex.md](draft-spec-codex.md)

## 1. 結論(先に要点)

**A の設計思想と B の実装の身軽さを組み合わせる。**

| 論点 | 採用 | 理由 |
| --- | --- | --- |
| 共有インターフェース | A: `{position, tempo, confidence}` の 3 値 | 追従器を差し替えても UI・伴奏が無改修で済む。最初から守る価値が最も高い設計判断 |
| 実装言語(初期) | B: Python | 追従アルゴリズムは試行錯誤が本体。C++ は精度が出てから移植を判断する(A 自身も未決事項として挙げている) |
| 特徴量 | A: chroma を主、f0 は補助 | ビブラート・ピエゾの基音の弱さ・重音に頑健。f0 は演奏後フィードバック(セント偏差)に使う |
| 追従器 | A: Online DTW → HMM。ただし **自作せず `matchmaker` を使う** | 参考実装が既にオンライン追従・シミュレーションモードを持つ。自作は精度が頭打ちになってからで良い |
| 伴奏 | A: MIDI + ソフト音源(FluidSynth) | テンポ変更・シーク・停止が無劣化。オーディオ伴奏は将来拡張 |
| 入力 | B: マイクも対象にするが、**推奨はライン入力 or ヘッドホン運用** | 回り込みを前提から外せばエコーキャンセルが不要(A の前提を運用で担保する) |
| UI | A: Web 技術 + OpenSheetMusicDisplay | MusicXML を実用的に描画できるライブラリが事実上これしかない。Python の Qt で譜面を描くのは遠回り |
| プロセス構成 | A: 音声処理と UI を別プロセス、WebSocket で 3 値を配信 | UI 側の GC やレンダリングで音声処理が止まらない。Python 側を後で C++ に差し替えても UI は無改修 |
| 検証 | A: リプレイ基盤を最初から | 毎回弾いて調整する運用は破綻する。録音 + オフライン DTW で正解データを作る |
| 段階 | A のロードマップを B の MVP 精神で圧縮 | 「一定テンポで合奏が成立する」を最初の到達点にする |

## 2. 各案の評価

### 2.1 ドラフト A(Claude 案)の強み・弱み

強み:

- 3 値インターフェースによるモジュール分離。
- 「f0 を直接推定しない」「MIDI は時間が自由変数」「先読みスケジューリングは必須」など、失敗パターンを先回りした判断が多い。
- リプレイ基盤、演奏後フィードバックを早期成果物にする、UI をデバッグビューアとして先に作る、といった検証戦略が具体的。
- follower と judge の分離、フレーズ単位採点など、将来のゲームモードへの布石も筋が良い。

弱み:

- C++20 の Audio Core、lock-free リングバッファ、WASAPI 排他など、**個人開発の初期に背負うには重い**。追従精度が出る前に基盤で消耗するリスクが高い。
- 電子バイオリン限定を前提にしており、アコースティック + マイクを切り捨てている。
- 5.3 ms バッファや < 2 ms/step などの数値目標は、Python プロトタイプでは意味を持たない。

### 2.2 ドラフト B(Codex 案)の強み・弱み

強み:

- MVP の範囲が現実的(1 パート、短い曲、一定拍子、先頭から開始)。
- 開発ステップが「まず音程検出を検証」から始まり、動くものを早く得られる。
- マイク入力も対象にしており、機材の敷居が低い。

弱み:

- 「音程 + 発音時刻を検出して音符列と照合する」方式は、**スラー(オンセットなし)・ビブラート・同音連打で崩れやすい**。バイオリンの特性と相性が悪い。
- 位置推定・テンポ推定・伴奏制御の境界が曖昧で、後から差し替えにくい。
- 譜面表示を Python/Qt で行う前提だが、MusicXML の描画は Qt 側に成熟したライブラリがない。
- 回り込み(スピーカー音がマイクに入る)への対策が書かれていない。

## 3. 採用する構成(概要)

詳細は [../design/architecture.md](../design/architecture.md) を参照。

```
[マイク / ライン入力]
        │ 48 kHz mono
        ▼
 core(Python)                       ← 後で C++ に置き換え可能
   audio-io   : sounddevice
   feature    : chroma(CQT ベース)+ spectral flux
   follower   : matchmaker(Online DTW → HMM)
   tempo      : カルマンフィルタ
   accomp     : MIDI + FluidSynth、レート変調 + 先読みスケジューリング
   recorder   : 生音声・特徴量・推定値をすべて記録(リプレイ用)
        │ WebSocket(localhost, JSON, ~30 Hz)
        │ { position, tempo, confidence }
        ▼
 ui(Web: ブラウザ + Vite、必要なら Electron)
   OpenSheetMusicDisplay で譜面描画、連続値カーソル、confidence 可視化
   セッション後の音程・タイミング偏差オーバーレイ
```

## 4. 判断の理由(補足)

### 4.1 なぜ Python から始めるか

このプロジェクトの難所は追従アルゴリズムの調整であり、基盤の速度ではない。Python なら `matchmaker` / `partitura` / `librosa` をそのまま使い、録音ファイルに対するシミュレーションで精度を詰められる。3 値インターフェースと WebSocket 境界を守っておけば、core だけを後で C++ に置き換えられる。

### 4.2 なぜ chroma を主にするか

バイオリンはビブラートで ±50〜100 セント揺れ、スラー内ではオンセットが出ない。音名を離散化して音符列と照合する方式はここで崩れる。chroma(12 次元)+ DTW は連続特徴量の比較なので、この 2 点に構造的に強い。f0 は「演奏後にセント偏差を出す」用途で使えばよい。

### 4.3 なぜ MIDI 伴奏か

オーディオ伴奏はテンポ変更にタイムストレッチが必要で、音質劣化と遅延がある。MIDI はテンポ・シーク・停止が無劣化。音質は後から音源(SF2 / SFZ)で改善できる。

### 4.4 マイク入力をどう扱うか

パイプラインはライン入力と同じで良い。違いは伴奏の回り込みだけなので、初期は「ヘッドホン運用」を推奨条件にして回避する。スピーカー運用は将来の課題として残す。

## 5. 最初の到達点

**「一定テンポの短い曲で、演奏に合わせて伴奏が鳴り、譜面上のカーソルが追従する」**(A のロードマップの Phase 3 相当)。ここまでを最短で到達し、その後にテンポ追従(Phase 4)とミス耐性(Phase 5)へ進む。演奏後フィードバック(Phase 2)は追従が完成する前でも価値があるため、並行して早めに入れる。
