# violin-follow 仕様書

> リアルタイム楽譜追従による、バイオリン練習用自動伴奏システム

| | |
|---|---|
| プロジェクト名 | `violin-follow`（仮） |
| バージョン | 0.1（ドラフト） |
| 対象楽器 | 電子バイオリン（ピックアップ出力） |
| ステータス | 設計フェーズ |

---

## 1. 目的とスコープ

### 1.1 目的

演奏者のバイオリン演奏をリアルタイムに聴き取り、楽譜上の現在位置とテンポを推定して、伴奏を演奏者に追従させる。

### 1.2 コアとなる抽象

システム全体は、以下の 3 値を推定する問題に還元される。

```
{ position: float,    // 楽譜上の位置（拍単位、連続値）
  tempo:    float,    // BPM
  confidence: float } // 0.0 - 1.0
```

**この 3 値がシステムの唯一の共有インターフェース**である。伴奏エンジン、UI、ゲーム判定はすべてこの値のみを購読し、追従アルゴリズムの内部実装を知らない。追従器を差し替えても下流は無改修とする。

### 1.3 スコープ内

- 単一楽譜（MusicXML）に対する追従
- MIDI 音源による伴奏の同期再生
- 譜面表示とカーソル追従 UI
- 演奏後のフィードバック（音程・タイミング偏差の可視化）
- 演奏ミス、停止、弾き直しへの耐性

### 1.4 スコープ外（将来）

- 反復記号・D.C. の自動展開（初期は反復なし楽譜のみ）
- オーディオ録音伴奏のタイムストレッチ
- VST3 音源ホスティング
- 音楽ゲームモード
- アコースティックバイオリン（マイク入力）対応

### 1.5 前提条件

- 入力は電子バイオリンのライン出力。**伴奏の音響的回り込みは存在しない**ものとする。この前提により、エコーキャンセルを不要とする。
- 楽譜は事前に指定される。曲の自動識別は行わない。
- 演奏は基本的に単旋律。重音は追従を破綻させないことを目標とするが、精度保証の対象外。

## 2. 用語

| 用語 | 定義 |
|---|---|
| score position | 楽譜上の位置。四分音符 = 1.0 の拍単位、連続値 |
| follower | 楽譜位置を推定するモジュール |
| judge | 音符単位で演奏の良否を評価するモジュール（ゲームモード用） |
| beat map | 拍位置と実時間の対応表 |
| unfold | 反復記号等を展開し、線形なノート列に変換すること |

## 3. システム構成

### 3.1 全体構成

```
┌─────────────────────────────────────────────┐
│  電子バイオリン → オーディオIF               │
└──────────────────┬──────────────────────────┘
                   │ 48kHz mono
┌──────────────────▼──────────────────────────┐
│  Audio Core (C++20)                          │
│  ┌────────────────────────────────────────┐  │
│  │ audio-io      : 入出力・リングバッファ  │  │
│  │ feature       : CQT / chroma 抽出       │  │
│  │ follower      : 位置推定               │  │
│  │ tempo         : テンポ推定             │  │
│  │ accompaniment : 伴奏レンダリング        │  │
│  └────────────────────────────────────────┘  │
└──────────────────┬──────────────────────────┘
                   │ WebSocket (JSON, ~30Hz)
                   │ { position, tempo, confidence }
┌──────────────────▼──────────────────────────┐
│  UI (Electron + React + TypeScript)          │
│  ┌────────────────────────────────────────┐  │
│  │ OpenSheetMusicDisplay : 譜面描画        │  │
│  │ cursor renderer       : 位置カーソル    │  │
│  │ session view          : 演奏後の分析    │  │
│  └────────────────────────────────────────┘  │
└─────────────────────────────────────────────┘
```

### 3.2 プロセス分離の方針

Audio Core と UI は**別プロセス**とする。Electron のメインスレッド／レンダラの GC 停止がオーディオスレッドに影響しないことを保証するため。

通信は WebSocket（localhost）。音声データは通さず、推定値と制御コマンドのみ。帯域は無視できる。

### 3.3 スレッド構成（Audio Core）

| スレッド | 役割 | 制約 |
|---|---|---|
| audio callback | I/O、伴奏レンダリング | **ロック・メモリ確保・例外を禁止** |
| dsp | 特徴量抽出、follower、tempo | 周期実行、ブロッキング可 |
| ipc | WebSocket 送受信 | 低優先度 |

audio callback → dsp、dsp → audio callback の受け渡しはすべて lock-free リングバッファ経由とする。

## 4. データパイプライン

### 4.1 楽譜データの流れ

MuseScore プロジェクトを唯一のソースとする。

```
song.mscz
  │
  ├─ MuseScore CLI ─→ score.musicxml
  │                     ├─→ [UI]      OSMD で描画
  │                     └─→ [Backend] partitura で解析 → 参照ノート列
  │
  └─ MuseScore CLI ─→ accomp.mid
                        └─→ [Backend] 伴奏エンジン
```

変換コマンド:

```bash
MuseScore4.exe -o score.musicxml  song.mscz
MuseScore4.exe -o accomp.mid      song.mscz
MuseScore4.exe -j jobs.json                  # バッチ
```

**パート分けの規約**: バイオリンパートは MusicXML の `part-name` を `Violin` とする。それ以外のパートを伴奏として扱う。

### 4.2 ID 対応付けの方針

バックエンドと UI は別々に MusicXML をパースするため、音符の同一性を保証できない。

**採用方針**: バックエンドは音符 ID を返さない。拍位置（float）のみを返し、UI は `GraphicalMusicSheet.calculateXPositionFromTimestamp()` で描画座標に変換する。ID 照合を発生させないことで、この問題自体を回避する。

演奏後の分析など、音符単位の対応が必要な箇所では複合キー `(part, measure_index, voice, staff, chord_index, onset_beats)` を両側で決定論的に計算して照合する。

### 4.3 反復の展開

追従器は線形なノート列を要求するが、譜面表示は展開されない。

- partitura の unfold で展開したノート列を追従用とする
- 「展開後の拍位置 → 表示上の (小節, 拍)」の対応表を別途保持する
- **初期実装では反復を含む楽譜を対象外とし、バリデーションで弾く**

## 5. モジュール仕様

### 5.1 audio-io

| 項目 | 値 |
|---|---|
| サンプルレート | 48000 Hz |
| チャンネル | 入力 1ch（mono）、出力 2ch |
| バッファサイズ | 256 samples（5.3 ms） |
| API | Windows: WASAPI 排他 / ASIO、macOS: CoreAudio |
| ライブラリ | miniaudio または PortAudio |

前処理として、ピエゾピックアップの基音の弱さを補正するハイパスおよび EQ を挿入可能とする。係数は設定ファイルで調整可能とすること。

### 5.2 feature

| 項目 | 値 |
|---|---|
| ホップサイズ | 512 samples（10.67 ms、93.75 fps） |
| ウィンドウ | 4096 samples |
| 特徴量 | CQT ベースの chroma（12次元）、L2正規化 |
| 補助特徴 | スペクトラルフラックス（オンセット検出用） |

**f0 を直接推定しない。** バイオリンのビブラートは ±50〜100 セント変動し、ピエゾ入力は基音が弱くオクターブエラーを起こす。また重音で単音前提の推定が破綻する。chroma はこれら全てに対して頑健である。

### 5.3 follower

**Phase 1 実装: Online DTW（Dixon 2005 系）**

- 参照系列: 楽譜から合成した chroma 系列
- コスト関数: コサイン距離
- 探索窓: 前方 ±N フレーム（N は設定可能、初期値 512 ≒ 5.5 秒）
- 出力: 最尤パスの現在位置、および累積コストから導出した confidence

**Phase 2 実装: HMM / 状態空間モデル**

隠れ状態を (楽譜位置, テンポ) とし、カルマンフィルタでテンポの不確かさを明示的に扱う。ミス・飛ばし・繰り返しへの耐性を状態遷移として設計できる。

参考実装として `pymatchmaker/matchmaker` を Phase 1 の検証に用いる。同ライブラリは録音ファイルに対してオンライン追従を再生するシミュレーションモードを持ち、実機なしで精度検証が可能。

**ロスト時のフォールバック**: confidence が閾値を下回った場合、位置推定を停止せず、直前のテンポで外挿を継続する。同時に confidence を UI に伝播させる。

### 5.4 tempo

follower の出力する位置系列に対してカルマンフィルタを適用し、テンポを推定する。

- 状態: (position, tempo)
- 観測: follower の位置推定値
- 観測ノイズ: confidence から動的に決定する

出力するテンポは平滑化されたものとし、瞬間的な変動をそのまま伴奏に流さない。

### 5.5 accompaniment

#### 5.5.1 インターフェース

```cpp
struct IAccompanimentSource {
  virtual ~IAccompanimentSource() = default;
  virtual void seek(double beat) = 0;
  virtual void setRate(double rate) = 0;
  virtual void renderBlock(float* out, int frames) = 0;
  virtual void allNotesOff() = 0;
};
```

MIDI 実装とオーディオ実装を同一インターフェースに収める。上位ロジックは拍位置とレートのみを扱う。

#### 5.5.2 Phase 1: MIDI + サンプラー

音源は sfizz（SFZ / BSD）または FluidSynth（SF2 / LGPL）。

**この選択は音質ではなくアーキテクチャの理由による。** MIDI では時間が自由変数であり、テンポ変更・シーク・停止がすべて無劣化で行える。オーディオでは時間が信号に焼き込まれており、本システムの「時間の制御権を演奏者に渡す」という設計思想と構造的に衝突する。

#### 5.5.3 同期制御

**通常時 — 連続的なレート変調**

```
error      = position_est - position_playback
rate_raw   = tempo_est / tempo_score + Kp * error
rate       = clamp(slew_limit(rate_raw), 0.7, 1.4)
```

- `Kp`: 位置誤差を 10〜20 拍かけて吸収する程度の緩やかな値とする
- `slew_limit`: レートの変化率を制限する。推定ノイズをそのまま流すと伴奏が可聴なワウを生じるため必須
- クランプ範囲外を要求された場合は不連続シークに切り替える

**不連続時 — クロスフェード**

follower が飛躍・巻き戻し・停止を検出した場合、レート変調では追従できない。

- MIDI: `allNotesOff()` 後に短いリリースを与えてから `seek()`
- オーディオ: 10〜30 ms のイコールパワー・クロスフェード

**先読みスケジューリング**

検出レイテンシが存在する以上、反応型では必ず遅れる。伴奏イベントは推定位置とテンポから**未来の時刻を予測してスケジュール**する。先読み窓は 100〜200 ms。

### 5.6 UI

#### 5.6.1 譜面描画

OpenSheetMusicDisplay（BSD 系ライセンス、MusicXML → VexFlow）を採用する。TypeScript 製で Electron + React と直接統合できる。

カーソル位置は `Cursor` クラスの音符単位遷移ではなく、`GraphicalMusicSheet.calculateXPositionFromTimestamp()` を用いて連続値から直接座標を得る。これにより推定位置の連続性をそのまま描画に反映できる。

代替候補として Verovio（LGPL、SVG 出力、要素 ID による個別ハイライトと timemap が利用可能）を検討したが、ライセンスの取り回しと統合コストから Phase 1 では見送る。

#### 5.6.2 レイアウト

- **横 1 段の連続スクロール**を採用する。ページめくり型は追従が飛んだ際に視覚的に破綻するため
- 現在位置を画面の水平方向 1/3 に固定し、譜面を流す
- 先読み領域（次に演奏する小節）が常に視野に入ることを要件とする

#### 5.6.3 confidence の可視化

confidence をカーソルの不透明度または色で表現する。追従が失われている状態が UI に表れないと、ユーザーは障害と区別できない。

#### 5.6.4 演奏後フィードバック

セッション終了後、アライメント結果を用いて音符ごとに以下を譜面上にオーバーレイ表示する。

- 音程偏差（セント）
- タイミング偏差（ミリ秒）

**この機能は追従精度が完成する前に価値を提供する。** オフライン DTW の段階で実装可能であり、Phase 2 の主要成果物とする。

## 6. 非機能要件

### 6.1 レイテンシ予算

| 区間 | 目標 |
|---|---|
| オーディオ入力バッファ | 5.3 ms |
| 特徴量抽出（1 フレーム） | < 3 ms |
| follower 1 ステップ | < 2 ms |
| 検出レイテンシ（音の発生 → 位置更新） | 30〜80 ms |
| 出力バッファ | 5.3 ms |

人間のアンサンブルにおける許容非同期は ±20〜50 ms 程度であり、検出レイテンシ単体でこれを超える。**先読みスケジューリングによる補償が必須**であって、オプションではない。

### 6.2 精度目標

| 指標 | 目標 |
|---|---|
| 位置誤差 中央値（通常演奏） | < 50 ms |
| 位置誤差 95 パーセンタイル | < 150 ms |
| ロストからの再捕捉時間 | < 2 秒 |
| 完走率（意図的なミスを含む演奏） | > 95% |

### 6.3 リアルタイム制約

audio callback 内では、メモリ確保、ロック取得、例外送出、システムコールを行わない。伴奏レンダリングの最悪実行時間はバッファ長（5.3 ms）を超えないこと。

## 7. 検証戦略

### 7.1 リプレイ基盤

**初期フェーズから実装する。** 以下を全て記録する。

- 生オーディオ（48kHz PCM）
- 特徴量ストリーム
- follower の出力系列（position, tempo, confidence）
- 使用した楽譜とパラメータ

オフラインで follower のみを差し替えて再評価できること。実機で毎回演奏してチューニングする運用は成立しない。

### 7.2 評価データセット

- 自分の演奏を、難易度・テンポ・ジャンル別に録音
- 各録音に対して**オフライン DTW で正解アライメントを生成**し、目視で修正して正解データとする
- 異常系を意図的に含む録音を用意する（弾き直し、飛ばし、停止、明確なミス）

### 7.3 UI をデバッグビューアとして使う

譜面 UI は追従エンジンより先に完成させる。「MIDI を固定テンポ再生しながらカーソルが動く」状態は、そのままオフライン DTW 結果の目視検証ツールになる。

## 8. ロードマップ

| Phase | 内容 | 完了条件 |
|---|---|---|
| 0 | 譜面 UI + MIDI 固定テンポ再生 | カーソルが譜面上を正しく進む |
| 1 | 音声入力 + chroma 抽出 + 可視化 | レイテンシ実測値が予算内 |
| 2 | **オフライン DTW** + 演奏後フィードバック | 録音と楽譜が正しく対応、偏差が譜面に出る |
| 3 | オンライン追従 + 固定テンポ MIDI 伴奏 | 一定テンポなら合奏が成立 |
| 4 | テンポ推定 + 先読みスケジューリング | テンポ変化に伴奏が追従 |
| 5 | ミス・飛ばし・停止・休符への耐性 | 完走率 > 95% |
| 6 | オーディオ伴奏 + タイムストレッチ | — |
| 7 | ゲームモード | — |

Phase 3 で「一応合奏になる」。Phase 4 以降が「音楽的に気持ちいいか」の勝負であり、定量評価だけでは詰められず実演奏による調整が必要。**工数の大半は Phase 4〜5 に集中すると想定する。**

Phase 2 は追従の完成を待たずに独立した価値を出す。優先度を高く保つこと。

## 9. 既知のリスクと未決事項

### 9.1 技術リスク

| リスク | 影響 | 対策 |
|---|---|---|
| スラー内にオンセットが存在しない | オンセット依存の手法が失敗 | 連続特徴量ベースを採用済み |
| 同音連打・トリル・トレモロ | chroma だけでは区別不能 | スペクトラルフラックスを併用 |
| 長い休符・伸ばしで追従が迷子になる | 伴奏が暴走 | テンポ外挿によるフォールバック |
| ピエゾ入力の音色が想定と異なる | 特徴量の前提が崩れる | 実機での早期検証、EQ 前処理 |
| 重音（無伴奏曲など） | 追従精度の低下 | chroma で緩和。精度保証外とする |

### 9.2 未決事項

- follower を Python プロトタイプから C++ へ移植する判断基準を定めていない。Phase 3 の精度が確保された時点で決定する
- 反復展開の対応時期。Phase 5 以降とするか、より早期に必要か
- 伴奏音源の配布方法（SFZ / SF2 のライセンスと同梱可否）

## 10. 将来拡張: ゲームモード（Phase 7）

現時点では設計方針のみ記録する。実装は Phase 5 完了後とする。追従が不安定な状態でゲーム層を追加すると、障害の切り分けが不可能になる。

### 10.1 follower と judge の分離

**follower と judge は要求が逆を向く。** follower は「見失わないこと」に最適化され、寛容であることが正しい。judge は離散的・低遅延・公平であることが求められ、厳格であることが正しい。

**follower の出力を judge に流用しない。** 位置推定は平滑化されており、個々の音の良否の情報が失われている。両者を並列モジュールとして走らせ、follower が提供する位置アンカーを judge が利用する構成とする。

### 10.2 レイテンシの構造的解決

譜面が既知であるため、演出は**譜面のタイムラインでスケジュール駆動**できる。演奏入力はトリガーではなく**検証**として扱い、判定確定後に見た目を差し替える。体感レイテンシを構造的に消去できる。

### 10.3 評価軸

入力が連続量である点がボタン入力ゲームと決定的に異なる。

- 音程（セント偏差）
- タイミング（オンセット）
- 音価・持続
- 音質（スペクトル重心、倍音比）
- ビブラート（f0 変調の周期・深さ）
- 強弱（RMS 包絡）

**音程を離散判定にしない。** 実演奏では発音後 200 ms 程度かけて音程を寄せていく。「音符 = 1 発の攻撃」ではなく「音程が合っている間、出力が上がり続ける」連続的なマッピングが、楽器の物理・練習としての意味・ゲーム的な快感の三者と一致する。

### 10.4 判定単位

スラーにはオンセットが存在しないため、音符単位判定は原理的に失敗する。**フレーズ単位で採点する。** スラー問題を回避すると同時に、音楽的にも正しい単位となる。

### 10.5 公平性

**偽陰性（正しく弾いたのにミス判定）は偽陽性の 10 倍有害である。** 伴奏アプリでの誤りは「もたった」で済むが、ゲームでは信頼の喪失を招く。閾値は直感より緩く設定する。

退化戦略への対策として、「正しい音が鳴った」だけでなく「間違った音が鳴っていない」も評価する。

### 10.6 設計上の注意

音楽的難易度とゲーム的難易度を分離しない。譜面の難しさがそのままゲームの難しさになるようマッピングする。

音ゲー化は誤った行動を報酬しうる（力み、悪い姿勢、音色の犠牲）。**音質を評価軸に含めることが最も効果的な対策となる。**
